# Zentry for Android

The Expo app: issues, events, projects and notification settings, plus push
notifications. The design is in [DESIGN.md §19](../DESIGN.md).

`mobile/` is its own pnpm root, apart from the Worker's workspace. Install it
separately:

```powershell
pnpm --dir mobile install
```

## Android toolchain (Windows)

A local build needs JDK 17, the Android SDK and CMake 3.31. The build script
looks for them where these steps put them, in your user folder, and sets
`JAVA_HOME` and `ANDROID_HOME` for the build only:

1. JDK 17 (Temurin) unpacked to `%USERPROFILE%\.jdks\jdk-17.0.21+9`.
2. The Android command-line tools unpacked to
   `%USERPROFILE%\Android\Sdk\cmdline-tools\latest`, then:

   ```powershell
   & "$env:USERPROFILE\Android\Sdk\cmdline-tools\latest\bin\sdkmanager.bat" "platform-tools" "platforms;android-36" "build-tools;36.0.0" "cmake;3.31.6"
   ```

   Add `"emulator" "system-images;android-36;google_apis;x86_64"` for an
   emulator.

Why CMake 3.31: React Native's C++ builds nest each source's full path in its
object path, which passes Windows' 260 characters from a folder as deep as
`C:\Users\<you>\source\repos\zentry`. The ninja that comes with the SDK's
default CMake (3.22) cannot open such paths; the one with 3.31 can, as long
as Windows long paths are on.

## Build

```powershell
pwsh mobile/scripts/build-android.ps1
```

That writes `mobile/android/app/build/outputs/apk/release/app-release.apk`
(arm64 phones and the x86_64 emulator). `-Install` also installs it with
`adb`. The first build takes about ten minutes; later ones are quicker.

For working on the app, build a debug APK instead. It loads JavaScript from
Metro, so edits show on the emulator within a second or two:

```powershell
pwsh mobile/scripts/build-android.ps1 -Dev -Install
```

```powershell
npx expo start
```

Run the second in `mobile/`. For a local `pnpm dev` over plain http, set
`$env:ZENTRY_ALLOW_HTTP = "1"` before building.

`android/` is generated by `expo prebuild` from `app.json`, `app.config.ts`
and the config plugins, and is not committed. After changing those, delete
`mobile/android` (or run `npx expo prebuild --clean`) before building.

The release build is signed with the debug key, which is fine for installing
it yourself. A Play Store build needs its own key (`eas build` or a
`signingConfig`).

## Release builds

`.github/workflows/mobile-release.yml` builds a signed release APK whenever
`main` gets a change under `mobile/` (or from the Actions tab, "Run
workflow"), and publishes it as a GitHub release named
`mobile-build-<run number>`. Download the APK on the phone from the
repository's Releases page and open it to install. Each build has a higher
versionCode (the run number) and the same signing key, so it installs over the
last one. The repository is public, so its releases are too.

It needs these repository secrets (Settings, Secrets and variables, Actions):

| Secret | Value |
| --- | --- |
| `GOOGLE_SERVICES_JSON` | the contents of `mobile/google-services.json` |
| `ANDROID_KEYSTORE_BASE64` | the release keystore, base64-encoded |
| `ANDROID_KEYSTORE_PASSWORD` | its password |
| `ANDROID_KEY_PASSWORD` | the key's password (the same as the keystore's) |

The key's alias, `zentry`, is in the workflow itself: as a secret, GitHub
would mask the word "zentry" throughout the logs.

To make the keystore and its secret value (PKCS12 keystores have one
password for the store and the key):

```powershell
keytool -genkeypair -v -storetype PKCS12 -keystore zentry-release.keystore -alias zentry -keyalg RSA -keysize 4096 -validity 36500
```

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("zentry-release.keystore")) | Set-Clipboard
```

Use that, not `certutil -encode`, whose header and line breaks
`base64 --decode` rejects.

Keep the keystore and its password somewhere safe, outside the repository. A
build signed with any other key will not install over the existing app: the
phone would have to uninstall it first, losing its sign-in. That includes
local builds (`build-android.ps1` signs with the debug key), so the first
release build needs one uninstall of a locally built app, and local release
builds will not install over a release from CI.

The versionCode is the workflow's run number, which restarts at 1 if the
workflow file is renamed or recreated; every build after that would be older
than the last release and fail the workflow's check.

## Signing in

In the web UI open Settings, Mobile app, choose **Show sign-in code**, and
scan it with the app. On an emulator, choose **Copy link** and paste it into
the app instead.

The QR code points the app at `MOBILE_API_URL` (wrangler.jsonc): the ingest
host in production, since Cloudflare Access does not let a phone through to
the UI host.

### Against `pnpm dev`

Set `MOBILE_API_URL=http://10.0.2.2:8787` in `.dev.vars` (10.0.2.2 is the
host machine from the emulator), run `pnpm dev`, and build the app with
plain http allowed:

```powershell
$env:ZENTRY_ALLOW_HTTP = "1"; Remove-Item -Recurse -Force mobile/android -ErrorAction SilentlyContinue; pwsh mobile/scripts/build-android.ps1 -Install
```

Builds for real use leave `ZENTRY_ALLOW_HTTP` unset, so the device token
never travels unencrypted.

## Push notifications

The Worker sends pushes through Expo's push service, which hands them to
Firebase Cloud Messaging. That needs, once:

1. An Expo account and project: `npx eas-cli@latest login`, then
   `npx eas-cli@latest init` in `mobile/`. Put the project id it prints in
   `app.json` under `expo.extra.eas.projectId`.
2. A Firebase project with an Android app for the package `com.zentry.app`.
   Download its `google-services.json` into `mobile/` (it is git-ignored).
3. The FCM V1 service-account key uploaded to the Expo project:
   `npx eas-cli@latest credentials`, Android, Google Service Account, or the
   Expo dashboard. See <https://docs.expo.dev/push-notifications/fcm-credentials/>.
4. Rebuild the app (delete `mobile/android` first).

Until then the app works but cannot register for pushes. Settings says why
and offers to try again. On a phone, allow notifications when asked; each
type (issue alerts, workflow, spike protection, quota) has its own Android
channel and can be muted in the phone's settings.

Which notifications go by push is chosen per type and project, as for email:
in the app under Settings, Notifications, or on the web Notifications page.

